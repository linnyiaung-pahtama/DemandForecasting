# Order Plan Tool on PostgreSQL

## Why
The tool now runs on the company's AWS server, where the other apps are moving to PostgreSQL. The user chose
**PostgreSQL only**: SQLite support is removed, not kept as an option.

## Goals
- The backend stores principal settings, the settings change log and runs in PostgreSQL; behaviour, API and
  screens are unchanged.
- The database is chosen by settings, not a file path: `DATABASE_URL` (e.g.
  `postgresql://127.0.0.1:5432/demandforecasting`) plus `DATABASE_USER` / `DATABASE_PASSWORD` when the URL has
  no user (so the password needs no URL-encoding), read from the environment or `backend/.env`.
- The schema is created on first start (`CREATE TABLE IF NOT EXISTS`), at today's version 8.
- A one-time tool copies an existing SQLite file (`orderplan.db`, version 8) into an empty PostgreSQL database,
  keeping IDs, moving the ID counters, and checking row counts.
- Tests run against a PostgreSQL test database, each test in its own throwaway schema.

## Non-goals
- No change to calculations, files, API shapes or screens.
- No UAM sign-in (still none).
- The v1 to v8 SQLite upgrade code is removed; a SQLite file older than v8 must be opened once with the old
  version (which upgrades it) before being copied.

## Design
- **`app/config.py`**: loads `backend/.env` if present (python-dotenv, already a dependency); exposes
  `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`. `ORDERPLAN_DB` goes away.
- **`app/db.py`**: `connect(url, schema=None) -> psycopg.Connection` with dict rows; `init_schema(conn)` creates
  the three tables. Types mirror SQLite's storage exactly: `TEXT`, `INTEGER`, `REAL` -> `double precision`,
  `INTEGER PRIMARY KEY AUTOINCREMENT` -> `integer GENERATED BY DEFAULT AS IDENTITY`; JSON stays `TEXT` (stored
  byte for byte); dates stay ISO `TEXT` as today. The unused v5/v7 columns (`holding_months`,
  `order_cycle_months`) are kept, so old change-log lines and copied data stay intact. `schema` (tests only)
  sets the `search_path`.
- **`app/repository.py`**: `Repository(url, schema=None)`; same methods. SQL changes: `?` -> `%s`,
  `lastrowid` -> `RETURNING id`. `ON CONFLICT ... DO UPDATE` and `LIMIT` stay. One connection per call, as
  today (commit on success, rollback on error).
- **`app/main.py`**: `create_app(database_url=None, schema=None)` instead of `db_path`.
- **`app/copy_from_sqlite.py`** (new): `python -m app.copy_from_sqlite <orderplan.db>` reads the SQLite file
  (Python's built-in `sqlite3`, only here), refuses unless its `user_version` is 8 and the target tables are
  empty, copies the three tables in one transaction keeping IDs, sets the identity counters past the highest ID,
  and prints source and target counts.
- **`requirements.txt`**: `psycopg[binary]`.
- **Tests**: `conftest.py` requires `TEST_DATABASE_URL` (+ `TEST_DATABASE_USER` / `TEST_DATABASE_PASSWORD`)
  and gives each test a fresh schema, dropped afterwards. Tests that opened SQLite directly use the test
  connection instead. The v1 to v8 upgrade tests are removed; the copy tool gets its own test (a v8 SQLite file
  in, matching rows and a working next ID out).
- **README**: the Database section describes PostgreSQL, the settings, the copy tool and the test database.

## On the AWS server (done by Lin, guided)
1. Create database `demandforecasting` and login `df_app` (owner), password `PG_DF_PW` in `/root/pg-secrets.env`.
2. Deploy the new code (push to `main`, with the auto-deploy workflow committed too).
3. Stop the app, copy `backend/data/orderplan.db` with the copy tool, write `DATABASE_*` into
   `/srv/demandforecasting/backend/.env`, start the app, check a saved plan opens.
4. Keep `orderplan.db` as the fallback until the user is happy.
